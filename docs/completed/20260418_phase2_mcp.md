# Phase 2 MCP (2026-04-18)

## Summary

Exposed Phase 1 Firestore read APIs as MCP tools and extended `firestore_query_collection` while keeping the legacy `{ collection_path, field, op, value, limit? }` shape valid.

## Tools added

| Tool | Role |
|------|------|
| `firestore_list_collection_ids` | Lists sub-collection IDs (optional `parent_doc_path`, paging). |
| `firestore_aggregate` | Aggregation with JSON `aggregators` and optional `where` (Firestore filter shape or shorthand `{ field, op, value }`). |
| `firestore_explain_query` | `explain_query` via JSON `spec` (QuerySpec-like) and optional `analyze`. |
| `firestore_explain_aggregate` | `explain_aggregate` with same inputs as aggregate plus optional `analyze`. |

## `firestore_query_collection`

- **Required:** `collection_path` only (schema relaxed from the old four required fields).
- **Legacy:** When `filter` is absent and `field`, `op`, and `value` are all present, and there is no `order_by` / `start_at` / `end_at` / `offset`, behavior matches the previous single-field filter + optional `limit` (still using primitive JSON values via `json_to_value`).
- **Extended:** Optional `filter` (Firestore REST shape: `compositeFilter`, `fieldFilter`, `unaryFilter`, or shorthand `field` + `op` + `value`), `order_by`, `start_at`, `end_at`, `offset`, `limit`. If `filter` is set, it overrides any legacy `field` / `op` / `value`.
